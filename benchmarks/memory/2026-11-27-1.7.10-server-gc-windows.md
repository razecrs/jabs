# Memory, Stability & Boot: Minecraft 1.7.10 Dedicated Server (JABS Native GC vs. HotSpot)

**Result:** With one player on identical worlds, JABS's native `server.exe` uses about **2x less memory** than vanilla `1.7.10-server.jar` on JDK 25 (1.9–2.4x less Private RAM, 1.25–1.6x less Working Set, against a JVM started with `-Xms64m` so its start heap does not count against it), and its memory stayed flat for 10 minutes (`137.9 MB` at 60 s, `134.6 MB` at 600 s). HotSpot is much faster under load, and this already shows at an ordinary player count: **with 20 players the native server held only ~14 TPS standing still and fell below 2 TPS once they walked, while the JVM held 20 TPS throughout**. HotSpot also boots sooner (`3.39 s` vs `5.79 s` warm, `5.79 s` vs `16.38 s` with fresh world generation), and in a 200-player stress test it delivered chunks about 3.7x faster. JABS wins on memory; today HotSpot wins on throughput from about 20 players up, so the native server is not yet a replacement for a busy server.

## One player: memory and boot

Driven by [`tools/bench_1_7_10_server.py`](../../tools/bench_1_7_10_server.py) in clean directories:
- **Cold:** empty directories, `level-seed=42`, so both engines generate the same world.
- **Warm:** copies of that `world/`, then a 600 s session of one bot (`benchbot`) that receives the spawn chunks (`0x26 MapChunkBulk`) and answers keepalives.

Without `-Xms`, HotSpot starts with 1/64 of physical memory as its heap and G1 commits all of it: `InitialHeapSize = 512 MB` on this 31.9 GB machine, and an empty Java program already shows `516 MB` committed. That reservation, not the server, is most of the default JVM's Private RAM, so the JVM was measured twice: with its default start heap and with `-Xms64m`. Used heap (`jcmd GC.heap_info`) is listed for the `-Xms64m` run.

## 20 players

The same bots and phases as the 200-player test below (5 minutes stationary, then 5 minutes walking outward), with 20 bots, both engines at `-Xmx4G`. With 20 bots the Time Update packets arrive promptly, so TPS is measured (median over 10 bots per 15 s window).

| 20 bots | JVM `-Xmx4G -XX:+UseG1GC` | JABS native `-Xmx4G` |
|---|---:|---:|
| Boot to `Done` (fresh world) | **`6.8 s`** | `18.4 s` |
| All 8,820 spawn chunks delivered after | **`< 15 s`** | `~45 s` |
| **Stationary TPS** | **`20.0`** | **`~14`**, 15 `"Can't keep up!"` |
| Stationary Private RAM | `~655–680 MB` (512 MB start heap committed, 95–365 MB used) | **`~186 MB`** |
| **Walking TPS** | **`19.0–20.5`** | `10` → `6` → `2.5` → `1.6`, then too far behind to measure |
| Walking: new chunks delivered in 5 min | **`28,665`** | `23,471` |
| Walking: Private RAM at the end | `834 MB` | `447 MB` |

The native server cannot keep 20 TPS with 20 players (it does with 5), and walking players outrun it. Its memory stays far lower, but the JVM figure here includes its 512 MB start heap, so the stationary ratio is not claimed; see the one-player section for the like-for-like comparison.

## 200 players (stress test)

This is a stress test, not a typical load: vanilla 1.7.10 servers usually host far fewer players, and at 200 even the JVM needed 3 GB to keep up with the walking phase.

Driven by [`tools/bench_1_7_10_crowd.py`](../../tools/bench_1_7_10_crowd.py): 200 offline bots log in at 20 per second, answer keepalives, confirm the server's position like a client and, once the server has sent Join Game, send a `Player` packet every second. Each engine runs 5 minutes **stationary** (all at spawn) and then 5 minutes **walking** (every bot climbs 30 blocks and flies outward at walking speed in its own direction, `allow-flight=true`). Both engines ran with `-Xmx4G`. The bots count the chunk columns each server delivered, which is the work behind its memory.

| 200 bots | JVM `-Xmx4G -XX:+UseG1GC` | JABS native `-Xmx4G` |
|---|---:|---:|
| Boot to `Done` (fresh world) | **`5.4 s`** | `20.4 s` |
| All 200 online | 200/200 | 200/200 |
| All 88,200 spawn chunks delivered after | **`~62 s`** | `~230 s` (3.7x slower) |
| Stationary Private RAM (after delivery) | `~675 MB` (512 MB start heap committed) | **`~234 MB`** |
| Stationary `"Can't keep up!"` | 4 | 3, up to 80–110 s behind |
| Walking: new chunks delivered in 5 min | **`+88,506`** | `+1,980` |
| Walking: Private RAM at the end | `3,025 MB` | `1,141 MB` |
| Survived both phases | yes | yes |

Stationary, both servers did the same work (the same 88,200 chunks): the native one needed about **2.9x less Private RAM** and took **3.7x longer**. Walking, the native server fell far behind: it loaded terrain (memory grew to 1.1 GB) but sent only 1,980 new chunks against HotSpot's 88,506, so its walking memory is **not** a like-for-like comparison and no ratio is claimed for it. Throughput under load is JABS's open problem; HotSpot's JIT is well ahead there.

TPS under this load could not be measured reliably from the client: Time Update packets queue behind megabytes of chunk data. Vanilla's `/debug` profiler counts ticks on the server, but it slows the native server from 20 to 6–8 TPS while the JVM stays at 20, so it would measure itself and was not used.

Before `-Xmx` was honoured natively (public `ea91a9e`), the native heap was fixed at 512 MB and this run ended in `OutOfMemoryError` once the bots started walking.

## Build times

The native server's compile (`jabs compile`, class files to C) and build (`jabs build`, 113 C sources on 12 jobs, `--opt 2`):

| Step | Time |
|---|---:|
| Compile + cold build (no object cache) | `176 s` total, of which `jabs build` `159 s` |
| Rebuild after a runtime change (99 of 113 objects from `--cache`) | `42 s` total, of which `jabs build` `21 s` |

## Environment, reproducibility & caveats

| | |
|---|---|
| JABS | One player: the Immix + LOS GC commit (public `a3c6693`, "Add cooperative Immix + LOS garbage collector and tighten object layouts"). 200 players and build times: public `ea91a9e` ("Size the GC heap like -Xmx …"), with `-Xmx4G`. `--opt 2`, Clang 22.1.8 with LLD, MinGW target |
| Build inputs | `local/` profiles that include a JVM trace of a real client joining (`--executed-methods`, `--loaded-classes`): the server creates packets by reflection (`Class.newInstance` from its packet table), and a build without the join trace drops their constructors and cannot accept a connection. The one-player binary was `120,539,648` bytes |
| Scripts | [`tools/bench_1_7_10_server.py`](../../tools/bench_1_7_10_server.py) (`--engines`, `--jvm-opts`) and [`tools/bench_1_7_10_crowd.py`](../../tools/bench_1_7_10_crowd.py); Mojang-free, they need a local `1.7.10-server.jar` and a built `server.exe` |
| Machine | Intel Core i7-9750H @ 2.60 GHz (6 cores / 12 threads), 31.9 GB RAM, Windows 11 Home 10.0.26300 |
| JVM | Microsoft OpenJDK 25.0.4.101 with G1 |
| Caveats | One run per configuration. One player: a stationary bot receiving the spawn chunks. 200 players: bots in one Python process on the same machine, so they compete with the server for CPU on both engines. No entity-heavy or redstone workloads and no client rendering |
