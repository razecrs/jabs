# Server startup: stock JVM vs JABS launch optimizations

**Result:** median time to `Done` went from **7.7 s to 3.6 s (2.1× faster)** for the
Minecraft 26.3 dedicated server, existing world, 5 interleaved runs each.

This measures startup only. Tick time, world generation, client frame rate and
memory were not measured and are unaffected by these optimizations.

## What was compared

| | Stock | JABS |
|---|---|---|
| Command | `java -Xmx2G -jar 26.3-server.jar nogui` | `jabs run server-26.3.json --until-ready` |
| Classpath | Mojang's bundler jar (loads the game through its own class loader) | Bundler unpacked, nested jars verified and put on the classpath |
| Game jar | Signed (as shipped) | Local unsigned copy (`strip_signatures`) |
| JVM AOT cache | None | Trained once by `jabs prepare` (JEP 483/514) |
| JVM flags | `-Xmx2G` | `-Xmx2G` plus `-XX:AOTCache=…` |

Both sides run the same Mojang server jar (SHA-256 verified by JABS), Java,
world, `eula.txt` and `server.properties`. No game code is changed.

## Method

1. Close other applications. Remaining: Windows services, Malwarebytes
   (real-time protection on), an idle ProtonVPN service, NVIDIA and WebView2
   helpers. 21.5 GB RAM free.
2. One warm-up run per side, discarded (the game files are on a hard disk;
   the first read is much slower).
3. Five runs per side, alternating stock and JABS, so both see the same
   machine state.
4. Each run: start the process, wait for the server's
   `Done (...)! For help, type "help"` line, record wall-clock time since
   process start, send `stop`, wait for exit.

Timing comes from outside the process: a small Python driver for stock, and
`jabs run`'s own report for JABS. Both start the clock at process spawn.

## Results

| Run | Stock | JABS |
|---|---:|---:|
| warm-up (discarded) | 14.7 s | 6.2 s |
| 1 | 7.6 s | 4.9 s |
| 2 | 9.0 s | 4.1 s |
| 3 | 7.7 s | 3.6 s |
| 4 | 7.7 s | 3.6 s |
| 5 | 7.7 s | 3.6 s |
| **Median** | **7.7 s** | **3.6 s** |
| Mean | 7.9 s | 4.0 s |
| Min / max | 7.6 / 9.0 s | 3.6 / 4.9 s |

All runs exited with code 0. JABS reported `unbundle: verified and reused`,
`strip_signatures: game jars run from local unsigned copies`,
`aot_cache: used existing cache` on every run.

## Costs and caveats

- **Training:** `jabs prepare` performs one training start (38 s on this
  machine) and writes a 140 MB cache. It must be redone when the JDK build,
  JVM flags or game jars change. `jabs run` never trains on its own; without
  a cache it starts unoptimized (8.1 s, about stock speed).
- **One machine, one configuration.** No confidence interval is claimed from
  five runs. JABS's first two runs (4.9 s, 4.1 s) were slower than the
  steady 3.6 s, which suggests the cache file was still being read from the
  hard disk.
- **Startup only.** This says nothing about gameplay performance, and it is
  not comparable to Horizon's published client frame rates.
- An earlier run on the same machine with many background applications
  open (including 44 Snipping Tool processes) measured stock at 8.6–9.0 s
  and JABS at 4.4–6.0 s. Background load inflates both sides.
