# Coverage: Minecraft 1.7.10 server with java.base

**Result:** 99.4% of the server jar's methods compile (58,342 of 58,671), but only 64%
are self-contained (37,304): about 21,000 compiled methods can still reach code that did
not compile. Those methods are not held back by one blocker. Six blocker categories each
reach almost the same ~20,700 methods, so fixing any one of them alone unlocks little.
The largest root behind them is in `java.base`: **564 native methods with no JABS
implementation**. A single unsupported opcode, **`multianewarray`** (26 uses in total),
also sits on the path to about 20,700 methods.

This is a static measurement of what the compiler can reach through the dependency graph.
It does not say which methods the server actually runs. Nothing was launched or timed.

## What was measured

`jabs coverage` compiles every class of the jar, plus `java.base` from the given JDK, as
one unit without writing C. It reports, per blocker category:

- `direct`: methods unsupported for that reason;
- `reaches`: compiled methods whose dependencies (calls and class initializations, followed
  transitively) include a method or class blocked by that category;
- `unlocks`: of those, the methods no other category reaches, so fixing this category
  alone would make them self-contained.

## Reading it

- The same ~20,700 server methods (and ~31,800 `java.base` methods) are reached by at least
  six categories at once. They form one connected core, and "unlocks alone" is near zero for
  most of them because every method in the core is blocked by several categories. The core
  shrinks only when its blockers are fixed together.
- Native methods in `java.base` are the largest root: 564 direct, and through them the most
  reached methods on both sides. The server jar has no native methods of its own; its
  20,781 come entirely through `java.base`.
- `multianewarray` has the smallest direct count of the core categories (26) for a reach
  on the order of the whole core, which makes it the cheapest member to remove.
- `instanceof`/`checkcast` against interfaces or outside classes is the server's own largest
  independent blocker (143 methods unlocked alone).

## Caveats

- The first tables count every method of the jar. The loaded section narrows that to classes
  a real run loaded, but still counts every method of those classes, called or not; a
  method-level trace would narrow it further.
- "Unlocks alone" understates blockers that only matter in combination, which is the case
  for the core above. Ranking sets of categories (for example greedily: the category that
  unlocks most, then the next given the first) would show what to fix together.
- One run, one Minecraft version, one JDK. Newer versions use more `invokedynamic`
  (DataFixerUpper, Brigadier) and will rank differently.
- Category names come from `blocker_category`, which groups reasons by wording.
